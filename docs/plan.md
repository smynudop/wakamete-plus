# オンライン人狼サーバー

オンラインでプレイできる人狼サーバーを開発。

## ゲーム詳細
game.mdを参照のこと。


## 技術スタック

* typescriptで統一する
* pnpmを使ったモノレポ構成とする
* 開発用データベースにはDocker Composeで起動するMongoDB 8.0を使用する

### フォルダ構成
* server
 * サーバーサイド. node.js
* shared
 * serverとfrontendで共有する型定義などを配置
* frontend
 * フロントエンド. vite + vue

### スタック詳細
* server
 * expressでファイル配信
 * ゲーム部分はsocket.ioによるリアルタイム管理を行う。タイマー管理でのゲーム進行を行えるようにする
 * 役職の種族 (`species`)・陣営 (`side`)・人狼把握能力 (`knowsWerewolves`) は shared パッケージの役職プロパティに集約し、役職追加時はデフォルト値から異なる特性だけを定義する。
 * 人数別の配役は `server/src/role-sets.ts` に集約し、ゲーム開始処理と公開HTTP API (`GET /api/role-sets`) から共通利用する。人数は初日犠牲者を含む総人数とする。
 * HTTPアプリ、Socket.IOによるゲーム配信、ゲームロジックはそれぞれ別モジュールに分離する。
 * 公開ルームはインメモリのルーム管理層で複数管理し、Socket.IOの配信とフェーズタイマーをルーム単位に分離する。
 * ルーム作成者をゲームマスターとし、参加中のSocketは同時に1つのルームだけに所属する。
 * ゲーム中の情報はインメモリで管理する。ゲーム終了後5分間は公開チャットを受け付け、その後MongoDBへ保存してルームをクローズする。
   * `game`コレクションには1ゲーム1文書でログ以外の情報を、`log`コレクションには1ログ1文書で時系列順序とゲームIDを保存する。
   * 保存済みゲームの一覧は `GET /api/logs`、各ゲームの全ログは `GET /api/logs/:roomId` から参照する。α版では保存に失敗した場合もルームをクローズし、インメモリのリソース解放を優先する。
 * ルームのクローズ処理はルーム単位で多重実行を防止する。未開始のまま作成から3時間以上経過したルームは30分間隔の巡回で破棄し、進行中・終了後のルームは巡回破棄の対象外とする。

### 開発用MongoDB

初回のみ `.env.example` を `.env` にコピーし、必要に応じて開発用の認証情報を変更する。

```sh
cp .env.example .env
pnpm mongo:up
```

MongoDBはホストの `127.0.0.1:27017` にのみ公開される。アプリケーションからは
`.env` の `MONGODB_URI` を使用する。データはDockerの名前付きボリューム
`wakamete-plus_mongo-data` に保存される。

```sh
pnpm mongo:logs
pnpm mongo:down
```

`pnpm mongo:down` はデータを保持する。データも削除して初期化し直す場合は
`docker compose down --volumes` を実行する。

* frontend
 * vite + vueでhtmlをビルドし配置。expressで配信する。
 * 配信するビルド成果物はワークスペースルートの `frontend/dist` から自動検出する。ワークスペース構成を含めずにデプロイする場合は、`FRONTEND_DIST_PATH` に絶対パスを指定する。
 * Vue RouterのHistoryモードを利用したSPAとし、トップ、公開ルームのロビー、ルームごとのゲーム画面を持つ。
 * プレイヤーの復帰用セッショントークンはルームIDごとにブラウザへ保存する。
 * 開発サーバーでは `/development/game` に、実ゲームの状態とは独立して役職・フェーズ・参加状態などを変更できるUIプレビューページを提供する。
   * プレビューページは `import.meta.env.DEV` を境界に遅延ロードし、本番ビルドには含めない。
   * ゲーム画面本体を本番ページと共有しつつ、プレビューページはSocket.IOへ接続しない。
